# Таксономия провалов и рубрика агента-критика

Проектный документ контура «LLM → GraphSpec → валидатор → критик → человек».
Определяет: (§1) исчерпывающий перечень провалов **исполненного** задания,
(§2) какие из них проверяются детерминированно, а какие — LLM-суждением,
(§3) пробный прогон (probe) — общий вход обеих половин, (§4) I/O критика,
(§5) пороги по умолчанию.

## 0. Границы: что таксономией НЕ является

Зона **валидатора** (уже реализована, `core/graph/executor.py`) — вне таксономии:

| Кто ловит | Что |
|---|---|
| `GraphSpec.parse` | битый JSON, нет `id`/`type`, кривой формат ребра |
| `GraphExecutor._build` | неизвестный узел, висячий провод, несовместимые типы, двойное подключение входа, незаполненный обязательный вход, цикл, TASK внутри тела, конфликт финалов, рассогласование туннелей |
| `GraphExecutor.run` | исключение узла, исчерпание `meta.max_attempts` |

Всё это возвращается генератору дословным текстом ошибки (см.
`closed_loop_contract.md`). Критик получает **только** графы, прошедшие эти
слои. Таксономия ниже — про графы, которые «работают, но плохи».

Код провала стабилен (используется в корпусе, eval-наборе и логах петли).
Формат: `<Класс><номер>`. Классы упорядочены по убыванию тяжести по умолчанию.

## 1. Таксономия

### Класс A — фактическая корректность (ответ неверен как утверждение)

- **A1. Ответ не следует из условия.** Ответ зашит константой/текстом, а
  условие вариативно. Канонический пример — реальная ловушка из
  `exercises/graph_examples` (`choice_pool_limit`): пул функций в условии,
  ответ «Предел равен 1.» текстом — для части пула это ложь. Причина в графе:
  ответ собирается из `text`-узла, не связанного проводом с источниками
  условия.
- **A2. Ответ верен лишь на части пространства seed.** На «удобных» значениях
  утверждение верно, на краях диапазона — нет (деление на малые числа,
  вырождение при min/max, потеря знака). Причина: диапазоны источников шире,
  чем область корректности формулы ответа, и нет `constraint`/`guard`.
- **A3. Рассинхрон данных условия и ответа.** Условие и ответ питаются от
  РАЗНЫХ случайных источников (или разных ветвей), хотя должны от одних:
  в условии `#m#` от одного `random_natural`, в формуле ответа — другой.
- **A4. Единицы и размерности.** Числа верны, единицы нет/неверны/несогласованы
  (км против м, «Н» при массе в граммах и ускорении в м/с²).
- **A5. Потерянная многозначность.** Уравнение с несколькими корнями — показан
  один; ± при извлечении корня; ОДЗ/область сходимости не оговорены, а ответ
  зависит от них. Причина: ответ собран вручную (`formula`+`text`) вместо
  узла, возвращающего полное множество (`solve`).

### Класс B — вырожденность и разнообразие

- **B1. Вырожденный экземпляр.** Конкретный seed даёт нулевую/единичную/
  диагональную матрицу, полином, схлопнувшийся в константу, совпавшие корни
  «разных» — задание формально есть, работать в нём не над чем.
- **B2. Тривиальный ответ.** Ответ 0/1/−1/само входное выражение на большинстве
  seed; «вычислите производную x»; определитель, очевидный без вычислений.
- **B3. Обход целевого навыка.** Задание решается коротким путём, минуя
  тренируемый навык: «решите систему», а она диагональная; «разложите в ряд»,
  а функция — уже полином.
- **B4. Коллапс разнообразия.** Партиция должна порождать семейство, а
  различимых вариантов мало: `random_choice` из 2 элементов, диапазон 1..3,
  «случайная» матрица 2×2 из {−1,0,1} с повторами.
- **B5. Деформация распределения отбраковкой.** `guard`/`constraint` отбрасывают
  почти всё пространство: (а) предельный случай — исчерпание попыток (ловит
  валидатор), (б) тихий случай — выжившие значения кучкуются в углу диапазона,
  разнообразие есть формально, фактически нет; плюс хрупкость (см. F1).

### Класс C — соответствие запросу пользователя

- **C1. Не та тема/навык.** Просили интегрирование по частям — сгенерированы
  табличные интегралы; просили пределы — производные.
- **C2. Не тот формат задания.** Просили интерактивный тренажёр — выдан
  статический `static_task` (и наоборот); просили «условие+ответ», выдан
  только текст без проверяемого ответа.
- **C3. Не та сложность.** Уровень школы вместо втуза и наоборот; число шагов
  решения очевидно не соответствует запрошенному уровню.
- **C4. Неполное покрытие запроса.** Из составного запроса реализована часть:
  «система + проверка совместности» — система есть, проверки нет.
- **C5. Неоправданная сложность графа.** Запрос покрывается 5 узлами, построено
  25 с циклами и туннелями. Работает, но не сопровождаемо и хрупко; для
  корпуса такие примеры токсичны (модель выучит барокко).

### Класс D — формулировка и представление

- **D1. Неоднозначная/неполная постановка.** Непонятно, что найти; «найдите
  значение» без указания чего; условие полагается на контекст, которого нет.
- **D2. Битые маркеры.** В готовом тексте остался `#var#` (опечатка имени
  маркера — движок подставляет только совпавшие по имени входы).
- **D3. Дефекты рендера математики.** Сырой sympy-синтаксис в прозе (`x**2`,
  `sqrt(`, `Eq(`), двойные связки («= =»), матрица без окружения, LaTeX-мусор.
- **D4. Языковые дефекты.** Рассогласование падежей с подставленным числом
  («найдите 1 корней»), смешение RU/EN вне цитируемых терминов, опечатки.
- **D5. Ответ ссылается на не введённое в условии.** В ответе фигурирует
  обозначение/переменная, которой нет в условии.
- **D6. Ответ в непроверяемой форме.** Иррациональное число десятичной дробью
  без указания точности; «см. график»; форма, которую студент не может
  сверить со своей.

### Класс E — педагогика

- **E1. Несоразмерная вычислительная рутина.** Идея задания верна, но числа
  дают 6-значные промежуточные результаты/дроби с huge знаменателями —
  тренируется арифметика, а не навык.
- **E2. Структура провоцирует угадывание.** Ответ бинарный или из крошечного
  множества, и распределение вырождено (всегда «да», всегда «сходится»).
- **E3. Неканоничная форма ответа.** Ответ математически верен, но не в
  принятой в дисциплине форме: нефакторизованный многочлен там, где ждут
  разложение; ненормированный вектор; не приведённая дробь.
- **E4. Нестабильный тип задания между seed.** Один seed даёт предел, другой —
  матрицу (разные ветви `case`/`random_choice` меж тем, что должно быть одним
  типом): партиция теряет дидактическую идентичность, сложность неуправляема.
  Границу задаёт запрос: если пользователь просил «3 разных типа» — это норма.

### Класс F — здоровье генератора (поведение графа как программы)

- **F1. Хрупкость отбраковки.** Медиана попыток близка к `max_attempts`;
  работает сегодня, сломается при чуть ином диапазоне. Предвестник B5.
- **F2. Недетерминизм при фиксированном seed.** Повторный прогон того же seed
  даёт другое задание — узел использует глобальный `random` мимо `ctx.rng`
  (известно для `logic_circuit`; см. docs/graph_addon.md). Ломает
  воспроизводимость экспорта и тестов.
- **F3. Неприемлемое время исполнения.** Тяжёлая символика (integrate/dsolve
  на плохом выражении) — секунды на прогон; UI и массовая генерация страдают.
- **F4. Мёртвые подграфы.** Узлы вне конуса предков финального TASK:
  вычисляются (жадный исполнитель), не влияют на результат. Работает, но
  мусор и сигнал ошибки замысла (автор думал, что ветка участвует).

## 2. Рубрика: символьно (SYM) или суждением (LLM)

SYM-проверки работают над `spec` (статически) и/или над probe-отчётом (§3) —
изменений движка не требуют. HYBRID = SYM даёт дешёвый флаг-подозрение,
LLM подтверждает/снимает. Колонка SYM — прямое ТЗ на `critic/probes.py`.

| Код | Режим | Символьная процедура (если есть) |
|---|---|---|
| A1 | **HYBRID** | probe: `distinct_answers == 1` при `distinct_statements > 1` → флаг; spec: у поддерева answer нет общих random-предков с поддеревом statement |
| A2 | **HYBRID** | расширенный probe K=32: ошибки/NaN/аномальные величины на краях; «тихо неверные» — только LLM |
| A3 | **HYBRID** | spec: множества random-источников-предков statement и answer не пересекаются, хотя оба непусты → флаг |
| A4 | **LLM** | — (реестр единиц возможен позже, сейчас не строим) |
| A5 | **LLM** | смягчение: если ответ идёт через `solve` — многозначность покрыта узлом, флаг не ставится |
| B1 | **HYBRID** | probe: ответ ∈ {0, 1, −1, «»}, ответ == условию, det==0, доля таких seed > порога → флаг; допустимость решает LLM |
| B2 | **HYBRID** | тот же детектор, что B1 (доля тривиальных по всем seed), + LLM-оценка «есть ли работа» |
| B3 | **LLM** | — |
| B4 | **SYM** | probe: `distinct_statements/K` и `distinct_answers/K` ниже порогов при наличии random-источников в spec |
| B5 | **SYM** | probe: медиана/максимум `attempts`; разброс числовых ответов (все в узкой полосе диапазона → флаг) |
| C1 | **LLM** | — |
| C2 | **HYBRID** | spec: тип финала (`static_task`/`interactive_task`/`words_trainer`) сравнивается с требуемым из запроса, если тот формализован |
| C3 | **LLM** | — |
| C4 | **LLM** | — |
| C5 | **HYBRID** | spec: число узлов > κ·медианы по референс-графам той же категории → флаг; вердикт за LLM |
| D1 | **LLM** | — |
| D2 | **SYM** | probe: regex `#[A-Za-zА-Яа-я_0-9]+#` по plain-тексту statement и answer |
| D3 | **HYBRID** | probe: подстроки `**`, `sqrt(`, `Eq(`, `= =`, `oo` в прозаическом тексте (вне формульных блоков) → флаг; тонкие случаи — LLM |
| D4 | **LLM** | — |
| D5 | **LLM** | (грубый SYM — числа ответа отсутствуют в условии — даёт много ложных срабатываний, не включаем) |
| D6 | **LLM** | — |
| E1 | **HYBRID** | probe: |числовой ответ| > порога, длина дробной части > порога → флаг; соразмерность — LLM |
| E2 | **LLM** | probe подсказывает: `distinct_answers == 1..2` при бинарной форме |
| E3 | **LLM** | — |
| E4 | **SYM** | probe: statement-шаблоны (текст с числами/формулами, заменёнными на •) различаются между seed; допустимое число шаблонов = числу ветвей `case` в spec, иначе → флаг |
| F1 | **SYM** | probe: `attempts_p50 > 0.3·max_attempts` → warn; исчерпание на любом seed → block |
| F2 | **SYM** | двойной прогон каждого seed, сравнение plain-текстов; несовпадение → блокирующий флаг |
| F3 | **SYM** | probe: `wall_ms` на seed > порога |
| F4 | **SYM** | spec: обход предков от финального TASK; узлы вне конуса → флаг со списком id |

Итог разделения: **SYM-only: B4 B5 D2 E4 F1 F2 F3 F4** (8 проверок — пишутся
без всякого ИИ и покрывают целый класс F целиком); **HYBRID: A1 A2 A3 B1 B2
C2 C5 D3 E1**; **LLM-only: A4 A5 B3 C1 C3 C4 D1 D4 D5 D6 E2 E3**.
LLM-колонка — это и есть оглавление промпта агента-критика.

## 3. Probe — пробный прогон (общий вход SYM-проверок и критика)

Probe строится ПОВЕРХ существующего движка, без его изменений:

- прогнать граф на K фиксированных seed (по умолчанию `[0..7]`; для релизной
  проверки партиции — `[0..31]`), каждый seed — дважды (детектор F2);
- на каждый прогон снять: `seed`, `statement` и `answer` как plain-текст
  (`" ".join(block.render_plain() ...)` — есть у всех блоков), `attempts`
  (использовано попыток), `wall_ms`, `error` (текст, если упало);
- агрегаты: `distinct_statements`, `distinct_answers`, `templates` (тексты
  с заменой чисел/формул на •), `attempts_p50/max`, числовые значения ответов
  (где парсятся), `double_run_mismatch`;
- SYM-проверки из §2 прогоняются над этим отчётом + spec и пишут `flags`.

Отчёт сериализуем (JSON) и целиком вкладывается во вход критика: критик
рассуждает над фактически исполненными заданиями, а не над своей симуляцией
графа в голове.

## 4. I/O агента-критика

Вход:

```json
{
  "request":  {"description": "строка запроса пользователя",
               "constraints": {"task_type": "static|interactive|null",
                               "count_hint": null}},
  "graph":    { "...": "GraphSpec как в core/graph/spec.py, дословно" },
  "probe":    { "engine_commit": "...", "seeds": [0,1,2,3,4,5,6,7],
                "runs": [{"seed": 0, "statement": "...", "answer": "...",
                          "attempts": 1, "wall_ms": 12, "error": null}],
                "aggregates": {"distinct_statements": 8, "distinct_answers": 7,
                                "templates": ["..."], "attempts_p50": 1,
                                "attempts_max": 4, "double_run_mismatch": false},
                "flags": [{"code": "B4", "detail": "2 различимых условия из 8"}] },
  "catalog_version": "хэш выгрузки NodeRegistry"
}
```

Выход:

```json
{
  "verdict": "accept | revise | reject",
  "failures": [{"code": "A1", "severity": "block | warn",
                "evidence": "цитата из probe/графа, доказывающая провал",
                "fix_hint": "что изменить в графе (для петли исправления)"}],
  "confidence": 0.0,
  "summary": "одно предложение для человека"
}
```

Развилка: бриф просил бинарный accept/reject — добавлен третий вердикт
`revise`. Reject без пути исправления обрывает петлю и жжёт попытки там, где
провал устраним одной правкой (A1: «проведи провод от источника к ответу»);
`revise` с `fix_hint` — это то, что петля возвращает генератору, и по логам
именно он даёт дешёвые repair-примеры для корпуса.

Правило свёртки: любой `block` → вердикт не `accept`; `revise`, если у всех
block-провалов есть `fix_hint`, иначе `reject`. Только `warn` → `accept`
(предупреждения показываются человеку при утверждении).

Обязательное правило для промпта критика: каждый провал — с `evidence` из
probe (цитата условия/ответа/числа), без цитаты провал не засчитывается.
Это гасит галлюцинации критика — он стохастичен, и его вердикт без
доказательства не стоит ничего.

## 5. Пороги по умолчанию (калибруемые)

| Параметр | Значение | Комментарий |
|---|---|---|
| K seed обычный / релизный | 8 / 32 | seed фиксированы: 0..K−1 |
| B4: мин. доля различимых условий | ≥ 0.6·K | при наличии random-источников |
| B4: мин. доля различимых ответов | ≥ 0.4·K | ответы совпадают чаще условий — норм |
| B1/B2: доля тривиальных seed | > 0.25 → флаг | тривиальный = ответ ∈ {0,1,−1} и т.п. |
| F1: медиана попыток | > 0.3·max_attempts → warn | исчерпание → block |
| F3: время на seed | > 3000 мс → warn | UI-порог |
| E1: величина ответа | > 10⁴ или > 4 знаков дроби → флаг | |
| C5: узлов против медианы категории | > 2.5× → флаг | медианы — по graph_examples |
| Петля: revise-раундов критика | ≤ 2 | далее эскалация человеку |

Пороги живут в одном конфиге пробника и калибруются по мере накопления
корпуса; коды таксономии при этом не меняются никогда.
