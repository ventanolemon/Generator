# План дообучения собственной модели генерации графов

Цель: через несколько месяцев заменить внешнюю LLM на стадии S1 контура
(`closed_loop_contract.md`) собственной моделью. Документ фиксирует выбор
подхода, схему данных, алгоритм сбора корпуса дешёвыми моделями и метрики.
Написан так, чтобы исполнение не требовало сильной модели — только следования
плану.

## 1. Сравнение подходов и решение

| | (а) Без дообучения: сильная открытая модель + заземление + few-shot + constrained decoding | (б) SFT (QLoRA) поверх средней открытой модели |
|---|---|---|
| Инфраструктура | только инференс (или API) | инференс + однократно GPU 24 ГБ на обучение |
| Нужен корпус | нет (few-shot из десятков) | да (≥ ~1000 generate + ~800 repair) |
| Качество на нишевом языке | среднее; вытягивается retrieval'ом | высокое на покрытых темах |
| Устойчивость к росту языка (новые узлы) | высокая (каталог в промпте) | средняя (см. решение о каталоге ниже) |
| Стоимость одной генерации | высокая (длинный промпт) | ниже (короче промпт, меньше модель) |

**Решение: этапами, (а) → (б), и (а) не выбрасывается никогда.**

- **Этап 0 — сейчас, без обучения.** S1 = сильная доступная модель;
  формат держат: JSON-схема GraphSpec через constrained decoding
  (vLLM `guided_json` / outlines / llama.cpp GBNF — любой доступный рантайм),
  few-shot — retrieval из принятых примеров. Этот этап одновременно и боевой
  режим, и маховик сбора корпуса (§4): каждая принятая генерация — обучающий
  пример. Дообучать до накопления корпуса нечего и не на чем — поэтому
  никакой GPU-инфраструктуры сейчас не требуется, и это не блокер.
- **Этап 1 — SFT, когда выполнены пороги:** корпус ≥ 1000 принятых generate
  + ≥ 800 repair, И eval-скор этапа 0 вышел на плато (две недели без роста
  при добавлении few-shot). База: **Qwen2.5-Coder-14B-Instruct** (сильный
  JSON/код, Apache-2.0, QLoRA влезает в одну карту 24 ГБ; бюджетный запасной
  вариант — Llama-3.1-8B-Instruct). Метод: QLoRA (r=16..32, на всех линейных
  слоях), лосс только на completion. Стек: axolotl или unsloth — оба дают
  конфиг-файл вместо кода; выбор по тому, что заведётся на месте.
- **Этап 2 — опционально, преференс-тюнинг (DPO/KTO)** на парах
  принято/отклонено, которые петля копит бесплатно (вердикты критика +
  человека). Только после того, как SFT-модель реально работает в S1.

**Решение о каталоге: каталог узлов остаётся в промпте и при обучении, и при
инференсе** (компактная форма: type_id, порты:типы, обязательные параметры).
Запекание каталога в веса фиксирует словарь языка — каждый новый узел
требовал бы переобучения; с каталогом в промпте модель учится ЧИТАТЬ каталог,
и рост языка её не ломает. Цена — длиннее контекст; компакт-версия каталога
(~115 узлов × 1 строка) — это единицы килобайт, приемлемо.

## 2. Два вида обучающих примеров (оба обязательны)

1. **generate**: описание → граф. Учит основной навык.
2. **repair**: описание + битый граф + дословные ошибки → починенный граф.
   Учит сходимости петли. Берётся бесплатно из логов (S2/S3/S5-раунды,
   закончившиеся успехом). Целевая пропорция в миксе: ~60/40 generate/repair;
   repair-примеры короче и их больше — балансировать выборкой, не сбором.

Формат сериализации примера — `training_example_schema.json`. Ключевой
инвариант: **target-граф хранится дословно в рантайм-формате
`GraphSpec.to_dict()`** (version/nodes/edges/meta, рёбра строками
`"node:port"`). Никаких учебных перекодировок — корпус исполняем движком в
любой момент (регрессия: каждый пример корпуса можно прогнать через
`GraphExecutor` при апгрейде движка и пометить сломавшиеся).

Промпт-шаблон SFT (фиксируется сейчас, чтобы корпус собирался сразу в нём):

```
system: Ты — компилятор описаний учебных заданий в JSON-граф. Отвечай только JSON.
        <КАТАЛОГ vX: ...> <ПРАВИЛА ФОРМАТА: ...>
user:   <описание>                                  # kind=generate
user:   <описание> + ПРЕДЫДУЩИЙ ГРАФ + ОШИБКИ       # kind=repair (формат repair-сообщения из контракта)
assistant: <JSON GraphSpec>
```

## 3. Алгоритм сбора корпуса дешёвыми моделями (исполняемый чек-лист)

1. **Матрица квот.** Оси: категория узлов (числовые/symbolic/linalg/ODE/
   control-циклы/case/списки/english/image) × форма задания (простое, с
   constraint/guard, цикл, пул вариантов, интерактив) × сложность (шк./втуз).
   Заполнять равномерно; пустые клетки матрицы — приоритет генерации.
2. **Описания.** Отдельный дешёвый промпт генерирует ЧЕЛОВЕЧЕСКИЕ описания
   под клетку матрицы (стиль преподавателя, 1–3 предложения, варьировать
   формулировки: «сделай», «нужны задачи на», «хочу партицию...»). Описания
   НЕ должны упоминать имена узлов — иначе модель выучит копирование, а не
   компиляцию.
3. **Генерация.** Каждое описание — через полную петлю контура (S1–S5,
   без S6). Принятые критиком — в карантин-корпус; repair-раунды — сразу в
   repair-корпус.
4. **Выборочная человеческая проверка карантина.** 10% случайных + все, где
   критик дал confidence < 0.7. Одобренные переходят в основной корпус с
   `human.approved=true`; вскрытые ложные accept'ы критика — в его eval.
5. **Дедупликация.** Канонический хэш графа: топосорт → переименование id в
   n0..nk → JSON без meta → sha256. Совпадение хэша ИЛИ косинусная близость
   описаний > 0.92 → дубль, отбрасывается. Квоты считаются после дедупа.
6. **Антисговор.** Критик при сборе корпуса — другое семейство моделей, чем
   генератор (или как минимум другая модель того же семейства + обязательные
   SYM-флаги). Генератор и критик одной модели дают согласованные ошибки —
   корпус отравляется тихо.
7. **Стоп-правила.** Тема с прохождением валидатора < 40% у дешёвой модели →
   заморозить тему, добавить 2–3 принятых примера темы в few-shot-ретривер,
   разморозить. Не тратить бюджет на лобовое добивание слабой темы.

## 4. Метрики (все считаются автоматически по eval_set.json)

| Метрика | Что меряет | Цель этапа 0 → этапа 1 |
|---|---|---|
| valid@1 | доля eval-кейсов, где 1-я попытка проходит S2 (сборку) | ≥ 60% → ≥ 85% |
| exec@K | ... и probe без ошибок на всех K seed | ≥ 50% → ≥ 80% |
| loop@V | ... сходится в пределах бюджета V=3 | ≥ 80% → ≥ 95% |
| checks | доля кейсов, где выполнены machine-checks eval-набора | ≥ 60% → ≥ 85% |
| repair@1 | доля repair-eval-пар, чинящихся с одной подачи ошибки | — → ≥ 80% |
| coverage | энтропия распределения категорий узлов в успешных генерациях | не падает между этапами |

Правило принятия модели этапа 1: SFT-модель заменяет этап 0 в S1 только если
не хуже по ВСЕМ метрикам и лучше по valid@1 и repair@1. Иначе — остаёмся на
этапе 0 и продолжаем копить корпус (это нормальный исход, не провал).

## 5. Чего не делать

- Не обучать на примерах без probe-отчёта и вердикта (грязный корпус хуже
  маленького).
- Не смешивать в одном обучении записи с разными `catalog_version` без
  перегенерации промптов под текущий каталог.
- Не собирать широкий корпус до фиксации схемы примера — переформатирование
  задним числом теряет провенанс.
- Не удалять этап 0 после запуска этапа 1: constrained decoding + петля
  остаются страховкой поверх любой модели.
