# Выдача предметов преподавателям

Админ раздаёт преподавателям доступ к предметам; преподаватель видит в витрине
только выданные. Документ фиксирует контракт между десктопом (Generator) и
сервером (GenerationWeb) — десктопная половина реализуется против него, не
дожидаясь серверной.

## Две особенности системы, определившие форму решения

**1. Все нынешние предметы — встроенные.** `bootstrap.sync_database`
пересоздаёт «Линейную алгебру», «Английский», «Физику», «Пределы»,
«Математический анализ», «Производные», «ОПВС» с зашитыми id на каждом старте
(`bootstrap.py`), а генераторы к ним берёт из `CODE_GENERATORS`. Сервер может
не отдать что угодно — десктоп тут же засеет их заново из собственного кода.

Следствие: **для встроенных предметов ограничение принципиально UI-уровневое.**
Генераторы едут в клиентском бинаре; спрятать их можно, изъять — нет. Настоящий
withhold возможен только для серверного контента (предметы с
`owner_user_id IS NOT NULL`, приезжающие через sync-pull). Мы делаем оба:
серверный скоуп pull'а для авторского контента и локальный фильтр витрины для
встроенного. Второе — защита от честной ошибки и «чтобы не мозолило глаза», не
от злого умысла; локальную БД её владелец правит как хочет.

**2. Курсорный pull не умеет в изменение прав.** `/sync/pull` — диф по
`row_version` (`core/sync/client.py`). Наивный «фильтр по выдачам» в нём тихо не
работает в обе стороны:

* **выдали** предмет — его `row_version` старая, курсор клиента давно её
  прошёл; предмет не приедет никогда;
* **отозвали** — `row_version` не менялась, события нет; предмет останется на
  машине навсегда.

Поэтому изменение выдач должно само быть событием синхронизации — см.
scope-эпоху ниже.

## Модель

```sql
CREATE TABLE subject_grants (
    teacher_login TEXT NOT NULL REFERENCES users(login) ON DELETE CASCADE,
    subject_id    INTEGER NOT NULL REFERENCES subjects(id) ON DELETE CASCADE,
    granted_by    TEXT NOT NULL,
    granted_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (teacher_login, subject_id)
);
```

Ключ — **логин**, не числовой `users.id`. Миграция 003 уже увела групповые FK на
логин, `core/session.py` фиксирует логин как канонический идентификатор, синк и
контур шлют `X-User-Id` строкой. Блокер «единой идентичности» из
`ui_rework_plan.md` тем самым снят — но разрешился он в обратную сторону от
рекомендации самого документа (там предлагалось тащить числовой id в сессию);
раздел документа поправлен.

Выдачи касаются только роли `teacher`. Админ видит всё всегда; студент витриной
предметов не управляет — ему контент приходит домашками.

## Умолчание: `default_subject_access`

Серверная настройка, два значения:

* `all` (по умолчанию) — преподаватель без единой выдачи видит **все** предметы;
* `none` — видит только выданные.

Так и должно быть настройкой, а не выбором навсегда. Строгий режим в день
выкатки оставит всех преподавателей с пустым экраном, пока админ не пройдёт по
списку; мягкий ничего не ломает и включает разграничение по мере раздачи.
Порядок раскатки: выкатили в `all` → раздали → переключили в `none`.

## Scope-эпоха: как изменение выдач доезжает до клиента

У каждого пользователя на сервере счётчик `scope_version` (целое). Он
инкрементируется при **любом** изменении, влияющем на видимый пользователю
набор: выдача, отзыв, смена `default_subject_access`, смена роли.

`POST /sync/pull` — запрос дополняется полем:

```jsonc
{ "device_id": "...", "cursors": {...}, "limit": 200,
  "scope_version": 7 }          // известная клиенту; 0, если не знает
```

Ответ дополняется полями:

```jsonc
{ "subjects": [...], "partitions": [...], "deleted": [...],
  "new_cursors": {...}, "has_more": false,
  "scope_version": 8,           // актуальная серверная
  "resync": true }              // scope_version клиента устарела
```

При `resync: true` сервер **игнорирует курсоры клиента** и отдаёт полный
доступный набор страницами с нуля. Клиент:

1. применяет страницы как обычно (upsert идемпотентен), запоминая id всего
   пришедшего за этот прогон;
2. **после последней страницы** (`has_more: false`) удаляет локальные предметы и
   разделы, которых в пришедшем наборе не было — *sweep*;
3. только теперь сохраняет `scope_version` из ответа.

Свойства: одинаково лечит и выдачу, и отзыв; идемпотентно; обрыв посреди resync
безопасен — sweep не выполнен, `scope_version` не сохранена, следующий sync
начнёт resync заново.

**Sweep не трогает встроенные предметы** (`owner_user_id IS NULL`): их всё равно
пересоздаст `sync_database` на следующем старте, а удаление увело бы за собой
разделы вместе с пользовательскими правками. Встроенные прячет фильтр витрины.

Альтернатива — синтетические tombstone'ы на пару (пользователь, предмет) —
отвергнута: требует таблицы на пользователя и путается при повторной выдаче.

## Эндпоинты

### `GET /subjects/grants/mine`

Свои выдачи. Зовётся десктопом при логине и при каждом sync.

```jsonc
{ "scope_version": 8,
  "default_access": "all",      // "all" | "none"
  "subject_ids": [1, 3, 10] }
```

`subject_ids` — явно выданные. При `default_access: "all"` и пустом списке
ограничения нет (см. «Поведение клиента»).

### `GET /admin/subject-grants`  (admin)

Данные матрицы одним вызовом.

```jsonc
{ "default_access": "all",
  "teachers": [ { "login": "ivanov", "fio": "Иванов И.И." } ],
  "subjects": [ { "id": 1, "subject_name": "Линейная алгебра",
                  "is_builtin": true } ],
  "grants":   { "ivanov": [1, 10] } }
```

### `PUT /admin/subject-grants/{login}`  (admin)

Полный набор выдач преподавателя — не дельта: матрица редактируется целой
строкой, идемпотентность важнее экономии.

```jsonc
{ "subject_ids": [1, 10] }
```

Ответ `{ "ok": true, "scope_version": 9 }`. Сервер инкрементирует
`scope_version` затронутого преподавателя.

### `PUT /admin/subject-grants/default-access`  (admin)

```jsonc
{ "default_access": "none" }
```

Инкрементирует `scope_version` **всем** преподавателям: переключение меняет
видимый набор у каждого, у кого нет явных выдач.

## Поведение клиента

Ограничение применяется, **только если оба условия выполнены**:

* задан адрес сервера, и
* есть локальный снимок выдач для текущего логина.

Иначе витрина не ограничивается. Иначе преподаватель без сети или до первого
успешного запроса терял бы все предметы — отказ сети не должен выглядеть как
отзыв прав.

Гость и админ не ограничиваются никогда. Гостю ограничивать нечего (он не
преподаватель), админ по определению видит всё.

Снимок живёт в локальных таблицах `SubjectGrants` / `GrantsMeta` (ключ —
логин, как у персональной видимости) и переживает перезапуск: витрина при старте
офлайн та же, что была онлайн.

## Взаимодействие с персональным скрытием

Это **разные измерения**, они не конфликтуют:

* выдача — *что мне позволено видеть* (решает админ, живёт на сервере);
* `SubjectVisibility` — *что я убрал с глаз* (решаю я, живёт локально).

Предмет показывается, когда выдан **и** не скрыт лично. Отзыв выдачи не трогает
персональные скрытия: вернут доступ — вернётся и прежний выбор «скрыт/видим».
