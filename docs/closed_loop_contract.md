# Контракт замкнутого контура: описание → GraphSpec → задание

Протокол петли «генератор (LLM) → символьный валидатор → probe → критик →
человек». Уровень — интерфейсы и инварианты; реализация оркестратора —
позже, точечно, любой моделью. Термины probe/коды провалов/I/O критика —
из `critic_taxonomy.md`.

## 1. Стадии

```
S0 заземление   → S1 генерация → S2 сборка → S3 probe → S4 SYM-флаги
                     ↑               │repair      │repair
                     └───────────────┴────────────┘
S5 критик ──revise──→ S1 (не более R раундов)
S6 человек (утверждение) → партиция constracted=4 + запись корпуса
```

- **S0. Заземление.** Системный промпт = компактный каталог узлов, выгруженный
  из `NodeRegistry` (type_id, категория, порты с типами, PARAMS_SCHEMA,
  description — всё уже есть у классов узлов) + таблица типов/конверсий +
  правила формата + 2–4 few-shot графа, подобранных retrieval'ом по описанию
  из принятых примеров корпуса (старт — `exercises/graph_examples`).
  Выгрузка версионируется: `catalog_version` = хэш содержимого; пишется в
  каждый лог и каждую запись корпуса.
- **S1. Генерация.** Вход: описание пользователя (или repair-сообщение, §2).
  Выход LLM: **только** JSON GraphSpec, без прозы. Где рантайм позволяет —
  constrained decoding по JSON-схеме GraphSpec.
- **S2. Сборка.** `GraphSpec.parse(...)` → `GraphExecutor(spec)`. Любая
  `GraphValidationError` → repair-сообщение → S1. Бюджет структурных раундов
  **V = 3**; исчерпан → эскалация.
- **S3. Probe.** Прогон на K seed (см. critic_taxonomy §3). Ошибка исполнения
  или исчерпание `max_attempts` на любом seed → repair-сообщение (с текстом
  ошибки и seed) → S1, в счёт того же бюджета V.
- **S4. SYM-флаги.** Проверки SYM/HYBRID-колонки над spec + probe. Блокирующий
  флаг (F2, исчерпание из F1) → repair; остальные флаги идут критику как вход.
- **S5. Критик.** Только для кандидатов, прошедших S2–S4 — **критик никогда не
  видит структурно невалидный или неисполнимый граф** (это главный инвариант
  контура: суждение расходуется на то, что уже нельзя проверить программой).
  `revise` → repair-сообщение с `failures[].fix_hint` → S1, бюджет **R = 2**;
  `reject` или исчерпание R → эскалация.
- **S6. Человек.** Видит: описание, 3–5 заданий из probe (случайные seed),
  warn-флаги, summary критика. Действия: принять / править в редакторе /
  отклонить. Принятие = запись партиции (`constracted=4`) + запись корпуса.

## 2. Формат repair-сообщения (единый для S2/S3/S4/S5)

```json
{
  "round": 2,
  "stage": "build | execute | probe | critic",
  "errors": [
    {"text": "ДОСЛОВНЫЙ текст GraphValidationError/исключения либо fix_hint критика",
     "seed": null,
     "code": null}
  ],
  "previous_graph": { "...": "ПОЛНЫЙ JSON предыдущей попытки, не диф" },
  "instruction": "Верни исправленный ПОЛНЫЙ граф тем же форматом. Меняй только необходимое."
}
```

Решения, зафиксированные здесь:

- **Текст ошибок передаётся дословно.** Сообщения движка уже человекочитаемы и
  называют узлы по id («Несовместимые типы: n4:out (number) → n7:text
  (words)») — пересказ только теряет точность. Никакой нормализации.
- **Всегда полный граф, никогда диф.** Модели ненадёжно применяют собственные
  дифы; полный JSON дороже токенами, но сходимость петли важнее.
- **Все ошибки одного раунда — одним сообщением** (S2 может дать несколько:
  собрать всё, что бросилось до первого фатального, но не чинить по одной).

## 3. Бюджеты и условия остановки

| Параметр | Значение | Исход при исчерпании |
|---|---|---|
| V — раунды сборки/исполнения (S2+S3+S4 суммарно) | 3 | эскалация «структурно не сходится» |
| R — revise-раунды критика | 2 | эскалация «качество не сходится» |
| Общий токен-бюджет на задание | конфиг | эскалация «дорого» |
| Успех | — | S6, ждём человека |

Эскалация — не сбой, а штатный выход: человек видит последнюю попытку, всю
историю ошибок и может дочинить в графическом редакторе (это дешевле, чем
писать граф с нуля). Частота эскалаций по темам — метрика качества заземления:
тема с высокой эскалацией = кандидат на новые few-shot примеры.

## 4. Детерминизм

- Все прогоны — с явным seed; probe использует фиксированный список 0..K−1.
  Wall-clock в выбор seed не входит нигде.
- Один и тот же (graph, seed) обязан давать одно задание (F2 из таксономии —
  блокирующий флаг: недетерминированный граф не принимается в партицию,
  пока узел-нарушитель не переведён на `ctx.rng`).
- `meta.seed` в сохраняемой партиции = null (боевая генерация случайна);
  seed probe живёт только в отчёте.

## 5. Что персистится (и это источник корпуса)

| Событие | Запись |
|---|---|
| Принято человеком | пример `kind="generate"` (описание → финальный граф) + probe + вердикты |
| Каждый успешный repair-раунд | пример `kind="repair"` (описание + битый граф + errors → починенный граф) |
| Эскалация | лог целиком, `kind="escalation"` (не для обучения напрямую; источник негативов и статистики тем) |

Repair-примеры — самый дешёвый и самый недооценённый продукт петли: они
учат будущую модель именно тому действию, которое делает петлю сходящейся
(чинить по тексту ошибки). Схема записи — `training_example_schema.json`.

## 6. Инварианты (сводка, для тестов оркестратора)

1. Критик не вызывается до успешного прохождения S2–S4.
2. Repair всегда содержит полный предыдущий граф + дословные ошибки.
3. Ни одна запись корпуса не создаётся без probe-отчёта.
4. `catalog_version` и `engine_commit` присутствуют в каждой записи.
5. Партиция создаётся только из S6 (человек), никогда автоматически.
6. Порядок бюджетов: V тратится до первого прохода S4; R — только после.
