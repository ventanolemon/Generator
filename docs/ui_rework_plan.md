# План: редизайн UI десктопа + переработка локальной БД

Дорожная карта работ по обновлению интерфейса десктопного приложения
(`Generator`, PyQt6) и архитектуры локальной SQLite-БД. Живой документ —
отмечаем волны по мере готовности, как `docs/graph_addon.md`.

## Принятые решения

- **Рез нагрузки:** backend↔презентация. Один исполнитель (Opus) ведёт слой
  данных/корректности, второй (Fable) — презентацию.
  - **Opus (я):** схема/миграции, `Repository`, безопасность (хэш паролей),
    протоколы-клиенты (sync-хуки, contour-клиент), бутстрап/сессия/роль,
    общая оболочка (TopBar, AppContext, хранилище настроек), тест-гейты
    логики, интеграция веток.
  - **Fable:** система темы и QSS, вёрстка всех окон/диалогов и полировка,
    консолидация каркаса превью, редизайн главных экранов и авторизации,
    Qt-smoke-тесты со скринами.
- **Единственный горячий файл** `ui/windows/generator_window.py` — **целиком
  за Opus** (структура/лейаут/TopBar). Fable создаёт новые окна и правит тему
  в листовых виджетах. Коллизий по файлам нет.
- **Скрытие И удаление** сущностей: скрытие = обратимый флаг (soft-delete),
  удаление = отдельное необратимое действие с подтверждением.
- **Адрес сервера один** для sync и контура: десктоп ходит только в
  `web_layer`, тот проксирует `/api/sync/*` и `/api/contour/*`. Роль
  teacher/admin приходит из сессии (A1) — ею гейтим кнопку контура.

## Модель координации

- Fable работает в изолированном git-worktree; Opus — в основном дереве.
- Один долгоживущий Fable-агент на все волны (единый дизайн-язык).
- Контракты (K1–K4) фиксируются в этом документе ДО параллельной работы —
  каждая сторона кодит против документированного API, не против чужих файлов.
- На границе волны Opus забирает работу Fable, интегрирует, гоняет весь набор
  (`QT_QPA_PLATFORM=offscreen python3 -m unittest discover -s tests`),
  открывает один draft-PR на волну (ветка перезапускается от master).

## Контракты (K1–K4)

### K1 — Тема (`ui/theme.py`, владелец Fable)

- Палитра-токены: `bg`, `surface`, `surface_alt`, `text`, `text_muted`,
  `accent`, `danger`, `success`, `border`. Два варианта: `light`, `dark`.
- `build_qss(palette) -> str`, `apply_theme(app: QApplication, name: str)`
  (читает `ui/theme` из настроек; по умолчанию `dark`).
- **Словарь QSS-классов** (через `widget.setProperty("class", …)` +
  селектор `QWidget[class="…"]`): `title`, `subtitle`, `card`, `toolbar`,
  `toolbtn`, `badge`, `badge-warn`, `badge-error`, `danger`, `muted`.
  Обе стороны используют ровно эти имена.

### K2 — Оболочка (`ui/widgets/top_bar.py` + `ui/app_context.py`, владелец Opus)

- `TopBar(QWidget)`:
  - `add_action(icon: str, tooltip: str, cb, *, roles: set[str] | None = None) -> QToolButton`
    — кнопка в баре; при `roles` показывается только для этих ролей.
  - `add_badge(key: str) -> QLabel` — правая зона статус-бейджей (sync).
  - `set_badge(key, text, level="")` — level ∈ {"", "warn", "error"}.
- `AppContext` (dataclass), пробрасывается в окна вместо россыпи аргументов:
  `repo`, `settings`, `sync_client | None`, `contour_client | None`,
  `user_id_provider`, `user_role_provider`.

### K3 — Настройки (`core/settings.py`, владелец Opus)

- Тонкая обёртка `QSettings` (org=`Generator`, app=`Desktop`).
- Ключи: `net/base_url`, `ui/theme`, `account/last_login`.
- API: `get_base_url()`, `set_base_url()`, `get_theme()`, `set_theme()`.

### K4 — Каркас превью (`ui/views/base_view.py`, владелец Fable)

- `BaseTaskView(QWidget)`: общая шапка (заголовок + кнопка «Сгенерировать
  заново») + прокручиваемый контейнер тела, наполняемый `render_blocks`.
- Хук `build_body() -> Iterable[Block]` переопределяют подклассы.
- От него наследуются `StaticTaskView`/`TableTaskView`/`InteractiveTaskView`/
  `TestExportView` и превью мастера контура (C2).

```
A1 → A2 → (B1 ‖ B2) → C1 → D1 → E

              B3 (Fable) после B2-API
              C2 (Fable) после C1
```

Backend-задача волны — критический путь Opus; презентационные задачи Fable
висят на её результате и идут параллельно внутри волны.

## Технические заметки

- **Пароли сейчас plain-text** (`Repository.find_user`: `WHERE login=? AND
  password=?`). D1 вводит `pbkdf2_hmac`; при первом входе старый plain-логин
  прозрачно мигрирует в хэш. Без D1 «смена пароля» бессмысленна.
- **Sync сейчас dormant:** `core/sync/` полностью реализован, но не вызывается
  из UI, а `Repository.upsert_partition/delete_partition` не кладут ничего в
  outbox. B2 добавляет хуки — иначе окно синка показывает пустую очередь.
- **Роль нигде не хранится:** `main.py` знает только `user_id`. A1 добавляет
  `user_role` в сессию — без неё нечем гейтить кнопку контура.
- **Блочный рендер уже общий:** все 4 view используют `render_blocks`/
  `Block.render_qt` (`ui/utils.py`) — дублируется только обвязка (K4 её
  консолидирует).

## Владение и роли (задача 3 + дизайн прав)

### Сделано на десктопе (безопасная половина задачи 3)
- `Subjects.owner_user_id` (nullable TEXT, `ensure_owner_column`, из bootstrap).
  NULL = встроенный предмет (сиды), виден всем. `Subject.owner_user_id` +
  `Subject.is_builtin`.
- Sync-pull переносит `owner_user_id`, ЕСЛИ сервер его прислал и колонка есть
  (совместимо и со «старым» сервером, и со «старой» БД).
- `list_subjects(owned_by=...)` — разграничение витрины (встроенные + свои).
  **Пока НЕ включено в UI** — см. блокер идентичности ниже.

### Блокер: единая идентичность (прежде access-control)
Десктоп знает пользователя как **строку-логин** (`find_user`→`login`,
`current_user["id"]`, ключ `WordStatsStore`), сервер — как **число**
(`owner_user_id`, `X-User-Id`). Пока типы не совпадают:
- фильтр `owned_by` по строке-логину против числовых владельцев с сервера
  показал бы учителю только встроенные предметы (свои — мимо) — поэтому
  ограничительный фильтр НЕ включаем;
- `queue_attempt`/правки уходят на сервер с `X-User-Id`=логин — не
  атрибутируются к числовому пользователю.

**Вывод: унификация идентичности — истинный фундамент для задач 2 и 3.**
Рекомендация: сессия несёт server-assigned числовой `user_id` (получается при
логине против web_layer); строка-логин остаётся как fallback для локального
режима без сервера. Локально созданные аккаунты (регистрация на десктопе)
получают локальный id, ремапящийся на серверный при первом sync (как
`local_ref` у партиций).

### Где живёт access-control
Разграничение «учитель видит только свои + встроенные предметы» — это
**серверный pull-scope**: `/sync/pull` отдаёт учителю только доступные ему
предметы. Десктоп фильтровать не обязан (получает уже суженный набор).
Локальный фильтр `owned_by` — лишь удобство витрины, не защита (локальную
БД её владелец читает как угодно).

### Роли: редактирование — server-authoritative, admin-only
Локальная колонка `users.role` — **кэш-отражение** серверной истины, не
источник прав. Правка роли в локальной БД НЕ должна давать привилегий:
сервер перепроверяет роль на каждом привилегированном вызове (заголовок
`X-User-Role` проставляет web_layer из JWT, а не клиент).
- **Кто:** менять роли может только `admin`.
- **Где:** отдельное окно «Администрирование», кнопка в TopBar
  `roles={"admin"}`, показывается ТОЛЬКО когда задан адрес сервера (оффлайн
  против локальной БД управление ролями бессмысленно и небезопасно).
- **Когда:** admin меняет роль другого пользователя → вызов на сервер →
  применяется у того при следующем логине/sync. Никакого self-elevation.

### Прочие возможности admin (все server-authoritative)
1. Управление пользователями: список, создание, деактивация, сброс пароля.
2. Группы + назначение учителей (задача 2): `groups`/`group_members`/
   `teacher_groups`/`assignments` (схема уже в GenerationWeb).
3. Глобальная аналитика: агрегаты по группам/партициям, метрики контура
   (`analytics.md`: `mv_group_progress`/`mv_partition_health`/
   `mv_contour_funnel`).
4. Встроенный контент: управление системными предметами (owner NULL),
   модерация принятого корпуса контура.
5. teacher видит и правит только своё; student — только решение и свою
   статистику.

### Рекомендованный порядок
1. **Унификация идентичности** (числовой user_id в сессии, ремап
   локально-созданных) — маленький фундамент, разблокирует владение,
   атрибуцию попыток и группы. ✅ (решение: id = login, сервер сведён —
   GenerationWeb PR #11)
2. Серверный pull-scope владения (GenerationWeb) → фильтр витрины на десктопе
   включается автоматически. ✅
3. ~~Группы + назначение учителей~~ — переставлено после окна
   администрирования (явный приоритет пользователя).
4. **Окно «Администрирование» (роли, пользователи)** — только с сервером.
   Сервер ✅ (GenerationWeb PR #12): `GET /admin/users` + `POST
   /admin/users/{login}/role` (`core/admin_api.py`), guardrails без
   self-elevation и без понижения последнего admin, 12 тестов. Десктоп —
   не начат: `AdminClient` (по образцу `ContourClient`), `AdminWindow`
   (PyQt), кнопка в TopBar `roles={"admin"}` только при заданном адресе
   сервера. Визуальный слой — черновой Fable-артефакт (таблица
   пользователей + confirm-флоу смены роли + матрица прав по ролям),
   контракт полей ложится на ответ `/admin/users` почти без изменений.
5. **Группы + назначение учителей (задача 2)** — сервер ✅ (GenerationWeb
   PR по группам): групповые FK сведены к логину (миграция 003), структурная
   группа (`groups`+`group_members`) — источник истины членства, засеивается
   из свободного `users."group"` (метка курса при регистрации) и держится
   согласованной в `create_user`. API: admin-CRUD `/admin/groups`
   (создание, состав, назначение преподавателей с guardrail'ами: непустое
   уникальное имя, существование группы/пользователя, роль teacher/admin для
   назначения) + teacher read-view `/groups/mine`. 15 тестов
   (`core/groups_api.py`, `core/test_groups_api.py`). Десктоп — read-only
   витрина групп у преподавателя + admin-управление в `AdminWindow`
   (следующим шагом). NB: `assignments` (партиция→группа, домашки) — отдельная
   будущая фича, схема есть, код не подключён.

## Пункт 1: унификация идентичности — находка и решение

### Находка (проверено по обоим репо)
«Несовпадение id десктоп↔сервер» оказалось **серверной внутренней
несогласованностью**, а не десктопным пробелом:
- Ответ логина web_layer `UserDto = (Login, Fio, Group, Email, …)` —
  **числового id нет**; пользователь идентифицируется **строкой-логином**.
- Вся request-идентичность сервера — строка: `current_user_id:
  ContextVar[str]` (generator_service/contour_service), `X-User-Id` строкой,
  статистика по `user_id=login`. Аутентификация клиентская, без
  сессий/JWT/токенов (`AuthEndpoints.cs`).
- НО в новой RBAC-схеме (`core/migrations.py`) у `users` есть числовой `id`
  (backfill из rowid), а `owner_user_id`/`group_members.user_id` — `INTEGER`,
  ссылаются на него. Эти числовые id **пока никто не читает**.

Десктоп уже консистентно использует строку-логин — совпадает со всем
реально связанным путём.

### Решение
**Канонический идентификатор пользователя — строка-логин, во всей системе.**
Минимальное изменение: так уже работает весь связанный путь. Числовой
`users.id` и `owner_user_id INTEGER` из RBAC-схемы — выбросы; их следует
свести к логину (или маппить), пока их никто не читает — это дешёвая
СЕРВЕРНАЯ правка (GenerationWeb), не десктопная.

### Сделано на десктопе
- `core/session.py::Session` — единый явный источник идентичности (login,
  role; `user_id` == login; guest = login None). Заменил ad-hoc словарь
  `current_user` в main.py; из сессии читают провайдеры AppContext, клиент
  синка (X-User-Id/role), контур, атрибуция попыток. Тесты: test_session (5).
- (Ранее, в задаче «статистика попыток») закрыт баг: `sync_client.user_id`
  не выставлялся при логине — push уходил без X-User-Id. Теперь из сессии.

### Разблокировано (решение принято: id = login)
- **owner-фильтр витрины ВКЛЮЧЁН** (`generator_window._owner_scope` →
  `list_subjects(owned_by=...)`): admin — все; гость — без фильтра;
  teacher/student — встроенные (owner NULL) + свои (owner == login). Пока
  все предметы встроенные, ничего не прячет; оживёт, когда сервер начнёт
  слать владельцев логином.

### Осталось на СЕРВЕРЕ (GenerationWeb, отдельный PR)
- Свести `Subjects.owner_user_id` (`migrations.py`, сейчас INTEGER) к логину
  (TEXT) и проставлять его при создании предмета = login автора.
- `/sync/pull` должен слать `owner_user_id` в payload предмета (десктоп уже
  умеет его принимать — `_apply_page`).
- Аналогично свести `group_members.user_id`/`teacher_groups.*` к логину для
  задачи 2 (группы).
